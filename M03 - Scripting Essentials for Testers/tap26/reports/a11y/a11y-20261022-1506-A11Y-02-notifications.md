## Findings

### A11Y-02 [serious] Unnamed logo links on notifications
- WCAG: 2.4.4 Link Purpose (In Context), Level A; 4.1.2 Name, Role, Value, Level A.
- Screen / element: `/notifications` · `header [data-test="app-name-logo"] a[href="/"]` and `a[href="https://cypress.io"]`.
- Found by: axe `link-name` (2 nodes per viewport), live DOM inspection, and keyboard Tab check.
- Who is affected: Screen-reader users navigating by links cannot identify either link’s destination or purpose. Keyboard users can focus them, but the missing spoken name makes them difficult to identify.
- Evidence:
  - Home logo: live `<a href="/">` contains only an SVG; `textContent` is empty, `aria-label` and `title` are null. Axe selector `.MuiTypography-inherit`.
  - Cypress footer: live `<a href="https://cypress.io" target="_blank">` contains only an SVG; `textContent` is empty, `aria-label` and `title` are null. Axe selector `a[target="_blank"]`. The sibling text “Built by” is outside the link and does not name it.
  - Both elements were flagged on desktop and mobile. Tab traversal focused the home-logo link and the footer link in both viewports.
- Source and fix:
  - [`NavBar.tsx`](../../src/components/NavBar.tsx), logo link around lines 142–160: add an accessible name such as “Real World App home”; treat the SVG as decorative when the link has a name.
  - [`Footer.tsx`](../../src/components/Footer.tsx), Cypress anchor around lines 11–26: add an accessible name such as “Cypress website” or visually hidden link text. “Built by” alone does not label it.
  - Verify both computed names in the accessibility tree after the shared UI fix.

The notifications navigation link (`data-test="nav-top-notifications-link"`) was not flagged by the `link-name` rule. This focused pass does not assess whether its badge-derived name is descriptive or whether its icon has an accessible name under other axe rules.
